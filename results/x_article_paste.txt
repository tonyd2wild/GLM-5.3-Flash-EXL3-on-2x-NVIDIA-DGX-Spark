NVFP4 vs EXL3 on DGX Spark: same model, same boxes, same minute (v2, corrected)

GLM-5.3-Flash, two 4-bit quants, two 2-node lanes of DGX Spark, benched simultaneously. Decode c1 to c6, time to first token on fresh prompts, prefill from 1.6K to 211K tokens, prefix caching, mixed load, context, KV pool, boot time, a 12-item reasoning battery and 40 real prompts across 8 categories. Plus the two things we got wrong, and how we found them.

[IMAGE: card_nvfp4_vs_exl3_v2.png]


THE SHORT VERSION

Split decision.

• NVFP4 is faster on fresh work. Decode 64.0 vs 61.5 tok/s single stream (+4%), +14 to 30% per stream at c2 to c5. Time to first token on fresh 1.6K prompts 1.29 vs 2.31 s at c1 and 4.5 vs 9.8 s at c6. Cold prefill on a fresh 211K-token prompt 2,763 vs 1,752 tok/s.

• EXL3 wins cached context, mixed load and headroom. Its prefix cache replays a 211K-token context in 0.8 s (NVFP4: 9.2 s) and a repeated 1.6K prompt in 0.52 s (NVFP4 gets no cache benefit below its 2,304-token block). Under a mixed load of four real prompts it does 43 vs 31 tok/s aggregate with a first token in 0.66 vs 1.97 s. It boots 1M context with a 1.40M-token KV pool (4.7x) on the same two boxes, in 13 min instead of 23.

• Quality is a tie. 40 real prompts, 8 categories: auto score 86% vs 85%, blind judge 9 wins NVFP4, 8 EXL3, 13 ties. 12-item reasoning battery: 11/12 vs 11/12 thinking off, 12/12 vs 12/12 thinking on. One real difference: with thinking off, EXL3 leaks self-correction into its answers and looped to the token cap twice; NVFP4 never did. Thinking on fixes it.

• We got two things wrong and fixed both. Run one had two Sparks clock-capped at ~700 MHz. Run two measured first-token latency by repeating one prompt, which EXL3 served from its prefix cache. Everything below is from fresh, distinct prompts unless the row says cache.


WHAT WE SERVED

Lane 1, NVFP4 (Reddie + Spark4)
• Weights: RedHatAI/GLM-5.3-Flash-NVFP4
• Runtime: vLLM, image ghcr.io/tonyd2wild/vllm-glm53-flash:sm121-v11-dflash2, the published 2-Spark recipe run verbatim
• Context 262,144. KV pool 295,230 tokens. KV dtype fp8_e4m3, MoE backend marlin (weight-only dequant; native FP4 MoE kernels for sm_121 are not upstream yet), enforce-eager
• Speculative decode: DFlash2 k=7. max-num-seqs 6. Prefix cache block size 2,304 tokens

Lane 2, EXL3 (Bluey + Asusi)
• Weights: brandonmusic/GLM-5.3-Flash-tr3-4bpw (EXL3 / TR3 4bpw)
• Runtime: vLLM + exllamav3 built for sm_121a, Reederey87's 2-Spark kit
• Context 1,048,576. KV pool 1,396,551 tokens. KV dtype fp8 (fp8_ds_mla), MoE exl3_moe trellis, enforce-eager
• Speculative decode: DFlash2 k=7. max-num-seqs 4 (caps c5 and c6; config, not the quant)

Neither lane is a roofline. The NVFP4 path is what vLLM can do on sm_121 today, the EXL3 path is exllamav3's first build for it. This is what ships on two Sparks right now.

Hardware: 4x NVIDIA DGX Spark (GB10, sm_121a, 128 GB unified memory), ConnectX-7 RoCE v2 fabric, two boxes per lane, tensor parallel 2. Bench client on a Mac mini over Tailscale.


HOW WE MEASURED

• Isolation. The relay our agents use was parked on another model, the latency monitor that sends real probes was paused, the three supervisor agents that default to this model were moved to a 27B on another box. Proven from each head's access log: NVFP4 head 128 chat requests in the window, all from the bench client; EXL3 head 129 from the bench client plus the kit's own 15-request warm-up burst fifteen minutes before the tests. Zero outside requests on either lane during any measurement.

• Simultaneity. Both lanes benched in parallel, same minute, same state. No shared GPUs, memory or NCCL group.

• Clocks. Healthy GB10 decode sits near 2,180 MHz at 95% utilization. After a reboot, two nodes were pinned at 611 to 728 MHz under load. All four verified at 2,171 to 2,190 MHz under a real request before this run.

• Fresh prompts. Every TTFT and prefill number below comes from a different prompt per request, so nothing can hit the prefix cache. Rows that say cache are the deliberate exception. Both engines JIT-compile kernels per request shape; two warm-up requests pay that first and are excluded.

• Settings. Temperature 0, thinking off unless stated. Decode sweep: one counting prompt (deterministic ~300-token output, comparable to the recipe's own peak test), 3 rounds per level, 5 at c1. Counting is the easiest sequence for the DFlash2 drafter, so it is a ceiling; the real-prompt section is the floor.

Prefill on a fresh 1.6K prompt: NVFP4 1,225 tok/s, EXL3 684 tok/s. EXL3 also pays a one-time compile of several seconds the first time it sees a new prompt-length bucket; we observed 7.8 s on a new ~2.4K length, then 1.3 s for different text at the same length.

For comparison, the identical prompt repeated: EXL3 0.52 s, NVFP4 1.54 s. That is the prefix cache, and it is the number we mistakenly published as first-token latency in version one.


PREFILL VS PROMPT LENGTH

Cold means a new prompt at that length: real prefill compute. Repeat means the identical prompt sent again: a prefix-cache hit, which measures the cache.

Cold prefill, tok/s (NVFP4 vs EXL3)
• 6,899 tokens: 1,482 vs 775 (EXL3 paid JIT here)
• 13,772: 1,559 vs 1,614
• 27,518: 1,876 vs 1,711
• 55,097: 2,384 vs 1,660
• 110,255: 2,684 vs 1,780
• 211,001: 2,763 vs 1,752

NVFP4 climbs with length; EXL3 is flat near 1,700. At 211K tokens NVFP4 is 58% faster. This matches what dfi measured at TP4 and posted in reply to version one.

Repeat of the identical prompt, seconds (NVFP4 vs EXL3)
• 6,899 tokens: 4.7 vs 0.4
• 55,097: 6.1 vs 0.5
• 211,001: 9.2 vs 0.8

EXL3's prefix cache is close to free at any length. NVFP4's helps at long lengths but still costs seconds, and does nothing below one 2,304-token block. An agent that re-sends the same long context every turn lives in this table.

REAL PROMPTS: 40 ACROSS 8 CATEGORIES

[IMAGE: chart_categories.png]

Five prompts each: coding, reasoning, JSON, HTML, prose, narrative, summarization, format following. Identical to both lanes, streamed so every prompt reports its own first-token time and decode rate. Graded automatically wherever there is a right answer: hidden tests executed against the code the model wrote, JSON parsed and compared exactly, HTML checked for the required structure, reasoning answers and format rules checked mechanically. Prose, stories and summaries were ranked by a blind pairwise judge (Qwen 27B on a separate box), each pair judged twice with positions swapped, a win counted only when both orders agree. Everything, including every failed check and every judge reason, is in the repo.

Decode depends on the workload, same on both lanes (tokens per second, NVFP4 vs EXL3)
• JSON 53 vs 50, HTML 53 vs 56, coding 48 vs 42, reasoning 48 vs 42
• prose 19 vs 20, narrative 19 vs 18, format 29 vs 21, summaries 37 vs 34
• counting, for reference: 64 vs 62

That spread is DFlash2 acceptance. Predictable text drafts well; prose does not. The counting number is a ceiling, prose is the floor, and it is the same floor for both quants.

Auto score, thinking off (NVFP4 vs EXL3)
• coding 100% vs 80%
• reasoning 100% vs 100%
• JSON 100% vs 100%
• HTML 100% vs 100%
• prose 75% vs 55%
• narrative 89% vs 76%
• summaries 60% vs 70%
• format 60% vs 96%
• overall 86% vs 85%

Blind judge, where rules cannot decide: NVFP4 9, EXL3 8, tie 13. Its reasons are almost all about who obeyed the length limit and who left a messy draft.

Thinking on, coding and reasoning: 100% vs 100%.

Mixed load, four different real prompts in flight: aggregate NVFP4 31.4 vs EXL3 43.4 tok/s, first token 1.97 vs 0.66 s, auto score 86% vs 84%.

The one behavioral difference. With thinking off, EXL3 leaks self-correction into its answers. It typed "when lo < hi" instead of "while" in a binary search, noticed, and rewrote the function nine times until it hit the token cap. It typed 1,045,576 in a table instead of 1,048,576, then "wait, I made an error" and redid the table three times. It wrote a 130-word explainer, then "let me count carefully" and re-drafted it four times to the cap. NVFP4 did none of that on the same prompts, 151 tokens against 900 on the bug fix. It could be the quant, it could be the kit's serving configuration; we do not know yet and we have flagged it to the kit's authors. Thinking on makes it disappear: 5/5 coding on both.

Both lanes overshoot word limits; it is a base-model habit. EXL3 overshoots harder.


QUALITY: THE 12-ITEM BATTERY

Three math word problems, three logic puzzles, two code items, a leap-year rule, the bat-and-ball trap, two strict-format tasks. Thinking off: 11/12 vs 11/12, same single miss (reversing the word "benchmark"). Thinking on: 12/12 vs 12/12, reasoning traces 341 vs 333 characters on average, near-identical. Published KLD-vs-FP16 figures put EXL3/TR3 4bpw near 0.025 and NVFP4 near 0.060, so a gap exists in the output distribution; neither the 12 items nor the 40 prompts resolved it. KLD is the instrument for that question, and it is next.


CONTEXT, KV POOL, BOOT

• Context that booted: NVFP4 262,144. EXL3 1,048,576.
• KV pool: NVFP4 295,230 tokens. EXL3 1,396,551 (4.7x).
• Boot to first healthy response: NVFP4 23 min (worker loads weights over NFS). EXL3 13 min.
• The NVFP4 recipe cannot boot at 1M context on these two boxes; there is no room left for the KV pool.


WHAT WE GOT WRONG

Part one, clocks. Our first run had EXL3 winning every metric by wide margins. Two of the four Sparks had come out of a reboot with GPU clocks pinned between 611 and 728 MHz. The tell was NVFP4's numbers not matching its own recipe's published peak. Restart, verify clocks under load, run everything again.

Part two, the prefix cache. Version one of this article said EXL3 answers first: 0.52 vs 1.54 s at c1 and 1.0 vs 4.6 s at c6, with a 2.9x prefill advantage. Every one of those requests carried the same prompt. EXL3 caches prefixes at fine granularity and replayed the cached KV; NVFP4's cache works in 2,304-token blocks, so a 1.6K prompt never hit it and NVFP4 did real prefill every time. A reader said EXL3 winning prefill on NVFP4-capable silicon made no sense. He was right. Re-measured with distinct prompts, NVFP4 leads first-token latency at every concurrency and prefill at every length above 14K.

Both mistakes were found by checking our numbers against someone else's. That is the point of publishing them.


WHICH ONE TO RUN

• Fresh single-shot work, short or long prompts, one or a few users: NVFP4. Faster decode, faster first token, faster long prefill.
• Agents that re-send the same long context every turn, many sessions in flight, contexts past 256K: EXL3. The prefix cache, the KV pool, the 1M context and the mixed-load numbers are all built for that.
• Either way, run thinking on for anything that must not loop, and warm the lane before you measure it.


PINS THAT MATTER

• NVFP4: run the published 2-Spark recipe verbatim. 256K context, worker first, head 25 s later. vm.swappiness=0 resets on reboot. Poll /health, never /v1/models.
• EXL3 kit: count_shards needs find -L on a symlinked HF cache. chown the vLLM cache dir on both nodes. It ships bound to loopback; set --host 0.0.0.0. The worker needs the full 164 GiB of weights locally.
• Both: roughly 91 GiB of weights per 121 GiB usable node. Drop page caches before every launch.
• Both: check GPU clocks under load after any reboot.
• Anyone benchmarking either: use a different prompt for every request, or you are measuring the cache.
